# TroubleShooting 文档命名与格式规范

| 项目 | 内容 |
| --- | --- |
| 适用范围 | `Docs/TroubleShooting/` 下的全部 TS 档案（文件名逐词用 `-` 连接，见第 1.1–1.4 节）。其余目录（`Docs/DevSpec/` 等）的文档用**大驼峰**（PascalCase）—— 见第 1.5 节 |
| 强制程度 | **强制** —— 新增 / 重命名档案一律按本规范；重命名后必须同步全部引用（见第 4 节） |
| 建立日期 | 2026-10-12 |
| 依据 | `Docs/TroubleShooting/TS-2610-001`、`TS-2610-002` 两份档案的实际结构；仓库既有「文件名用大驼峰 / 时间戳」约定的一次收敛 |

## 1. 文件命名规则

### 1.1 总格式

```
TS-<期间码>-<三位序号>-<英文标题词序>.md
```

| 字段 | 规则 | 示例 |
| --- | --- | --- |
| `TS` | 固定前缀，**全大写** | `TS` |
| `<期间码>` | 建立时的年月，`yyMM` 四位数字 | `2610` = 2026 年 10 月 |
| `<三位序号>` | 同期间内的顺序号，不足补 0 | `001`、`002` |
| `<英文标题词序>` | 标题的英文词序，**单词之间用 `-` 连接** | `Text-Composition` |

### 1.2 英文标题部分的硬性要求

| 规则 | 说明 | 反例 → 正例 |
| --- | --- | --- |
| **一个单词一个单词，用 `-` 连接** | 词与词之间必须有连接符，**禁止连写**、禁止下划线、禁止空格 | `CmdLfLineEnding` ✗ → `CMD-LF-Line-Ending` ✓ |
| **首个单词首字母大写** | 标题里的第一个单词通常用大写开头；**若首个单词本身就是缩写，直接全大写** | `lcd-Subpixel…` ✗ → `LCD-Subpixel…` ✓；`Cmd-LF-Line-Ending` ✗ → `CMD-LF-Line-Ending` ✓ |
| 其余单词沿用其固有写法 | 普通词首字母大写；**产品名按原厂写法逐字保留** | `GraalVM` ✓（不写 `Graalvm`）、`JavaFX` ✓ |
| **专有缩写可直接全大写** | 尊重行业与产品的使用习惯 | `LCD`、`CMD`、`JVM`、`CRLF`、`LF`、`WMI`、`GUI`、`UAC`、`TS`、`DPI`、`PE` ✓ |
| 不出现中文 | 文件名一律 ASCII；中文标题写在正文 H1 | `TS-2610-003-文本漂移.md` ✗ |
| 编号与标题都用 `-` 分隔 | 三段之间同样是连接符 | `TS-2610-001-LCD-Subpixel…` ✓ |
| 长度 | 建议 ≤ 90 字符；过长时精简为最能定性的 6–10 个词 | — |

### 1.3 词序怎么取

按「**对象 → 现象 → 处置/范围**」排，让同一目录内按文件名就能看出讲的是什么：

| 段落 | 写什么 | 示例 |
| --- | --- | --- |
| 对象 | 出问题的组件/机制 | `LCD-Subpixel`、`CMD-LF-Line-Ending` |
| 现象 | 观察到的异常 | `Text-Composition`、`Parsing-Drift` |
| 处置 / 范围 | 修复、预防、跟踪等 | `Fix-And-Prevention`、`Fix-And-Upstream-Tracking` |

### 1.4 正反例对照

| 反例（连写 / 大小写混乱） | 正例 |
| --- | --- |
| `TS-2610-001-LcdSubpixel-TextComposition-NativeImageFixAndUpstreamTracking.md` | `TS-2610-001-LCD-Subpixel-Text-Composition-Native-Image-Fix-And-Upstream-Tracking.md` |
| `TS-2610-002-CmdLfLineEnding-ParsingDrift-FixAndPrevention.md` | `TS-2610-002-CMD-LF-Line-Ending-Parsing-Drift-Fix-And-Prevention.md` |
| `TS-2610-003-JvmWmiCrash.md` | `TS-2610-003-JVM-WMI-Crash.md` |
| `TS-2610-004-lcd_subpixel_issue.md` | `TS-2610-004-LCD-Subpixel-Parsing-…md` |
| `TroubleShooting-Doc-Naming-And-Format-Spec.md`（DevSpec 文档，见 1.5） | `TroubleShootingDocSpec.md` |

### 1.5 不是 TS 档案的文档：用大驼峰（不要连接符）

`Docs/DevSpec/` 等目录下的规范 / 说明文档**不用** `TS-…` 前缀，也**不用连接符** —— 按仓库既有约定用大驼峰（PascalCase）：

| 规则 | 说明 | 示例 |
| --- | --- | --- |
| 单词紧邻、每个单词首字母大写 | 不用 `-`、不用 `_`、不用空格 | `TroubleShootingDocSpec.md` ✓ |
| 缩写保持全大写 | 尊重行业习惯 | `NativeImageCISpec.md` ✓ |
| 编号 / 日期不进文件名 | 需要版本就在正文里写 | `DocConventions.md` ✓ |

> 为什么两套规则：TS 档案名要把「编号 + 词序」都摆出来（便于按文件名排序列出），用 `-` 分隔读起来更清楚；
> 其余文档按仓库既有约定用大驼峰。两者都要求**不连写词、不用中文**。

## 2. 正文格式要求

### 2.1 骨架（各章节按此顺序）

| 顺序 | 章节 | 要求 |
| --- | --- | --- |
| 0 | 头部信息表 | 必须含：编号、标题、类型、首次发现、影响范围、当前状态、修复提交、相关文档 —— **一行一项** |
| 1 | H1 标题 | `# TS-<编号> · <中文标题>`；中文标题可用中文标点，专有名词用原文 |
| 2 | 现象 | 只写观察到的现象；有原始报错/日志就给原文 |
| 3 | 影响范围 | 受影响文件 / 场景；**是否会随发布包分发**必须有明确结论 |
| 4 | 结论分层 | 见 2.2，**必备** |
| 5 | 观测数据 | 见 2.3，**必备** |
| 6 | 定位过程 | 按步骤写，能复现他人推理路径 |
| 7 | 排除项 | 列已排除的可能及依据（写成表格） |
| 8 | 修复 | 按「改了什么 / 为什么这么改 / 为什么不那样改」组织；给出可回退方式 |
| 9 | 验证 | 区分「本地已验证」「CI 已验证」「真机待确认」 |
| 10 | 预防 | 如何防复发（机器强制优先于人工复查） |
| 11 | 未决问题 | 编号 Q1、Q2…；写清现状与阻塞点 |
| 12 | 相关文档 | 表格：文档/文件 + 关系 |

> 章节编号用 `## 1.` `## 2.`…，子节用 `### 1.1`。章节数量可按需增删，但**结论分层、观测数据、排除项、未决问题**四节不得缺。

### 2.2 结论分层（防止把猜测写成结论）

必须把结论拆成三层，逐层标注依据：

| 层 | 写什么 |
| --- | --- |
| 已观测事实 | 可复现的数字、字节、日志、命令输出 |
| 机制 / 行为模型 | 由事实推出的因果链；引用既有实测或上游源码 |
| 未定位 / 未复现 | 明确写「尚未定位」「本机无该环境」 |

禁止用「应该是」「估计是」这类表述替代分层结论；也禁止把「机制」写成「已在本机复现」。

### 2.3 证据的写法

| 要求 | 说明 |
| --- | --- |
| 命令 + 原始输出 | 例如 `git ls-files --eol`、`tr -cd '\r' < 文件 \| wc -c`、日志片段 |
| 数字优先 | 用具体数值（`CR=0 / LF=112`）而不是「行尾不对」这类形容 |
| 可复现 | 读文档的人能照着命令重跑一遍 |
| 对照 | 坏样本与好样本并列给出（如同一目录里合规的文件） |

### 2.4 排版细则

| 项 | 要求 |
| --- | --- |
| 表格 | **一行一项**，不得把多行压成一行；单元格内出现 `\|` 必须转义，否则表格会断 |
| 代码块 | 标注语言（```bash / ```powershell / ```cmd / ```text）；命令保留原文 |
| 语言 | 正文用简体中文；代码、命令、路径、报错原文、第三方专有名称按原文保留 |
| 链接 | 仓库内引用用相对路径；跨仓库引用写明仓库与分支 |
| 图片 | 放 `Docs/Asset/IMG/`，正文用相对路径引用 |
| 时间 | 用绝对日期（`2026-10-12`），不写「昨天」「上周」 |

## 3. 状态与更新

| 项 | 规则 |
| --- | --- |
| 状态取值 | `待定位` / `修复中` / `已缓解` / `已修复` / `已机器强制` / `已归档` |
| 更新方式 | **追加式**：新结论写进「定位过程」与「未决问题」，被否定的旧结论**保留并标注**，不要删掉 |
| 时间线 | 涉及外部依赖（上游 issue、他仓库）的档案，在相关章节维护「日期 → 事件」时间线 |
| 重命名 | 改名后**必须**同步更新全仓库引用（见第 4 节） |

## 4. 重命名操作流程

| 步骤 | 命令 / 动作 |
| --- | --- |
| 1 | `git mv 旧名 新名`（保留历史，不用删除再新建） |
| 2 | 全仓库查引用：`grep -rn "旧名" --include=* .`（忽略 `.git/`） |
| 3 | 逐个改成新名（相对链接、跨仓库链接、其他档案里的交叉引用、`Docs/README.md` 索引） |
| 4 | 校验残留：`grep -rn "旧名" .`（应无输出） |
| 5 | 提交（中文提交信息，写明 TS 编号） |

---

## 5. 提交前自查清单

| # | 检查项 |
| --- | --- |
| 1 | 文件名符合第 1 节：`TS-<yyMM>-<序号>-<词-词-词>.md`，无连写、无中文、无下划线 |
| 2 | 缩写/专有名词写法正确（`LCD`、`JVM`、`CRLF`、`GraalVM`…） |
| 3 | 头部信息表齐全，状态字段取值在允许集合内 |
| 4 | 有「结论分层 / 观测数据 / 排除项 / 未决问题」四节 |
| 5 | 证据均给出命令或原始数据，坏样本与好样本有对照 |
| 6 | 表格一行一项、无未转义 `\|` |
| 7 | 全文无残留旧文件名；`Docs/README.md` 索引已同步 |
| 8 | 若本次改动影响交付物行为，已在「验证」中区分本地 / CI / 真机 |
| 9 | 若非 TS 档案（`Docs/DevSpec/` 等），文件名用**大驼峰**（如 `TroubleShootingDocSpec.md`），不带连接符 |
